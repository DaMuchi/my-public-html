Die Kurzfassung

Das Video ist kein einzelner Kurs, sondern eine Aneinanderreihung von acht Vorträgen und Workshops. Die Kapitelmarken in der YouTube-Beschreibung passen nicht exakt zum Inhalt. Diese Seite folgt deshalb den tatsächlichen Vorträgen. Gemeinsamer Nenner: Claude liefert deutlich bessere Ergebnisse, wenn du ihm klaren Kontext, passende Werkzeuge und eine Möglichkeit zur Selbstkontrolle gibst.

1. Klar und strukturiert schreiben

Gute Anweisungen sind gegliedert, widerspruchsfrei und nennen beide Seiten einer Abwägung. «Mach es besser» genügt nicht.

2. Anweisungen ersetzen keine Fähigkeiten

«Rechne unbedingt richtig» macht Claude nicht besser im Kopfrechnen. Gib ihm ein Werkzeug (z. B. einen Rechner) statt eines Appells.

3. Messen statt raten

Mit festen Testfällen («Evals») siehst du, ob eine Änderung wirklich hilft. Das ist die Grundlage jeder Verbesserung.

4. Weniger ist mehr

Kurze Grundanweisung, Spezialwissen nur bei Bedarf nachladen («Skills»). Das spart Platz im Arbeitsspeicher von Claude.

5. Erst planen, dann machen

Lass dir von Claude einen Plan zeigen oder Rückfragen stellen, bevor es loslegt. Das spart teure Fehlversuche.

6. Vertrauen, aber prüfen

Claude darf viel erledigen. Sicherheit, Recht und Geschmack bleiben beim Menschen. Prüfen lässt sich vieles automatisieren.

Hinweis zur Aktualität Die Vorträge stammen aus unterschiedlichen Zeitpunkten. Genannte Modellnamen (Opus 4.7, Sonnet 4.6) und Details wie die 200'000-Token-Grenze in Vortrag 2 sind Momentaufnahmen und können sich geändert haben. Die Grundprinzipien bleiben gültig.

Glossar: Begriffe, die im Video fallen

Klicke auf einen Begriff, um die Erklärung zu öffnen.

Prompt

Die Anweisung oder Frage, die du an Claude schreibst.

System Prompt

Die Grundanweisung, die immer mitgeschickt wird: Rolle, Regeln, Tonalität. Der Nutzer sieht sie meist nicht.

Claude Code

Claudes Programmierassistent. Er läuft im Terminal, in der Entwicklungsumgebung (VS Code, JetBrains) oder im Web und kann Dateien lesen, ändern und Befehle ausführen.

Agent

Ein KI-System, das nicht nur antwortet, sondern selbständig mehrere Schritte ausführt: Werkzeuge nutzen, Ergebnisse prüfen, weitermachen.

Tool (Werkzeug)

Eine Funktion, die Claude aufrufen darf, z. B. «Datei lesen», «Web suchen», «Rechnen».

Skill

Ein Wissenspaket (Anleitung, Regeln), das Claude erst lädt, wenn es für die Aufgabe nötig ist. Wie ein Handbuch im Regal statt auf dem Pult.

Sub-Agent

Ein zweiter, getrennter Claude mit eigenem Kontext. Nützlich für parallele Arbeit oder als «frischer Blick» (z. B. Code-Review).

MCP

Ein Standard, um Claude an externe Dienste anzubinden (z. B. Dokumentation, Datenbank). Praktisch, kann aber viel Kontext belegen.

Kontextfenster

Der «Arbeitsspeicher» von Claude: alles, was es in einem Gespräch gleichzeitig berücksichtigen kann. Ist es voll, wird Claude unzuverlässiger.

CLAUDE.md

Eine Textdatei im Projekt mit Hinweisen für Claude (Projektaufbau, Teststart, Stilregeln). Wird bei jedem Start automatisch gelesen.

Eval

Ein fester Testfall mit erwartetem Ergebnis. Eine Sammlung von Evals zeigt, ob eine Änderung etwas verbessert oder verschlechtert.

Halluzination

Wenn die KI Fakten oder Zahlen erfindet. Das Video zeigt auch das Gegenteil: Claude verschweigt Wissen, das es hätte.

Harness

Die Software «drumherum», die Claude steuert: Schleife, Werkzeuge, Limits. Nicht das Modell selbst.

Claude Managed Agents

Anthropics gehostete Plattform für Agenten. Sie übernimmt Betrieb, Skalierung und Sicherheit, sodass man sich auf den Agenten konzentrieren kann.

Routine

Ein automatisch gestarteter Claude-Code-Auftrag, ausgelöst per Zeitplan oder Ereignis (z. B. neues GitHub-Issue).

Memory Store / Dreaming

Ein dauerhafter Notizspeicher für Agenten über mehrere Sitzungen hinweg. «Dreaming» räumt ihn im Hintergrund auf.

Adaptive Thinking / Effort

Einstellungen, wie viel Claude nachdenkt. Mehr Denken bringt oft bessere Ergebnisse, kostet aber Zeit und Tokens.

Der Prompting-Leitfaden

0:00 – 0:33Margot Vanlar, Applied-AI-Ingenieurin, Anthropic London

Am Beispiel eines Kundenservice-Bots einer fiktiven Telefongesellschaft («Meridian Mobile») wird Schritt für Schritt gezeigt, wie man einen bestehenden, gewachsenen Prompt repariert. Auslöser ist oft ein Modellwechsel, nach dem Testfälle plötzlich scheitern.

Das Vorgehen

1. Evals bauen5 Testfälle: ein einfacher Kontrollfall, Randfälle, und Fälle, in denen der Bot abgeben oder ablehnen soll.
2. AufräumenUnwahres entfernen («du bist ein Mensch»), Webseiten-Abfall löschen, mit XML-Tags gliedern.
3. Ausgabeformat festlegenFormat im Prompt beschreiben und technisch absichern (Stop-Sequenz, strukturierte Ausgabe).
4. Fehler einzeln behebenPro Fehlverhalten die Ursache im Prompt suchen und gezielt ändern.

Claude Code: Bewährte Arbeitsweisen

0:33 – 0:48Mitglied des Claude-Code-Teams (Name im Transkript abgeschnitten)

Eine kompakte Sammlung von Praxistipps für den Einstieg und für Fortgeschrittene. Hinweis: Der Vortrag stammt aus der Zeit der Claude-4-Einführung.

Grundlagen

  • CLAUDE.md anlegen. Claude hat kein Gedächtnis zwischen Sitzungen. Die Datei teilt Wissen mit dem ganzen Team: Teststart, Projektaufbau, Stilregeln. Es gibt sie pro Projekt, pro Unterordner und im Benutzerordner. Mit @datei lassen sich weitere Dateien einbinden.
  • Rechte steuern. Lesen darf Claude frei, Schreiben und Befehle werden erfragt. Häufige Befehle kannst du dauerhaft erlauben.
  • Kommandozeilen-Tools nutzen. Gut dokumentierte Tools (z. B. GitHub gh) sind meist besser als ein zusätzlicher MCP-Server.
  • Kontext verwalten. Bei voller Anzeige: /clear (frisch starten) oder /compact (zusammenfassen und weitermachen).

Effizient arbeiten

  • Erst Plan, dann Umsetzung. «Suche die Ursache und sag mir, wie wir es beheben» statt «Fix den Bug».
  • To-do-Liste beobachten. Wirkt sie falsch, mit Esc stoppen und umsteuern.
  • Kleine Schritte. Tests, Typ- und Stilprüfung, häufig einchecken, um zurückzufallen.
  • Screenshots einfügen. Claude versteht Bilder, z. B. ein Mock-up als Vorlage für eine Webseite.
  • «Think hard» im Auftrag. Neuere Modelle denken auch zwischen den Werkzeugaufrufen nach.

Tastenkürzel und Befehle

Claude auch ohne Bildschirm einsetzen (z. B. in GitHub Actions). Den öffentlichen Änderungsverlauf wöchentlich lesen, weil sich viel ändert.
Frage aus dem PublikumClaude hinterliess ungewollt erklärende Kommentare im Code. Das war ein Modellverhalten, das in Claude 4 deutlich besser wurde. Zudem folgt Claude 4 Anweisungen genauer: Es lohnt sich, die eigene CLAUDE.md zu entschlacken.

Wie Anthropic mit Claude Code arbeitet

1:33 – 2:03Arno, Architekt im Applied-AI-Team, Anthropic

Je länger ein Agent selbständig arbeitet, desto teurer ist ein falscher Start. Deshalb wird die Prüfung nach vorne verlagert: erst Anforderungen klären, dann Vorschau ansehen, dann die Prüfung in das Produkt einbauen.

1. Claude interviewt dichStatt alles vorab zu formulieren, lässt du Claude gezielte Rückfragen stellen (Hilfsmittel «AskUserQuestion»).
2. Vorschau als HTMLMehrere Designvarianten als anklickbare HTML-Seiten statt langer Markdown-Dateien. Verständlicher, dichter, besser zu kommentieren.
3. Prüfung eingebautDie App legt ihren Zustand offen, sodass Mensch, Agent und Automatik dieselben Prüfungen ausführen.

Guter vs. schlechter Prompt

Schlecht «Mach es besser.» «Keine Fehler bitte.»

Gut Bereiche nennen (Zielgruppe, Aufgabe), das Ergebnis offen lassen und Claude bitten, dich dazu zu befragen.

Idee dahinter: Claude kann oft besser herausfragen, was du wirklich willst, als du es vorab beschreiben kannst («Bitter Lesson»: Beschränke das Modell nicht unnötig).

Tipps aus der Praxis

  • Auto-Modus (Shift+Tab) sei «der beste».
  • Effort: Empfohlen wird «X-High» (/effort).
  • Fast-Mode (/fast) für schnellere Antworten.
  • Screenshots bei Layout-Problemen; neuere Modelle sehen deutlich besser.
  • Markdown-Dateien über ca. 200 Zeilen liest niemand.

Beispiel: Verifikation, die Claude selbst ausführen kann

An einer kleinen To-do-App zeigt der Referent, wie dieselben Prüfungen auf drei Arten laufen: als Dashboard für Menschen, durch Claude im Browser, und automatisch in der Entwicklungs-Pipeline.

Mensch

Dashboard mit Bestanden/Durchgefallen und Details. Ein absichtlicher Fehler («3 + 4 ≠ 10») wird sichtbar.

Agent

Claude liest den offengelegten Zustand und lässt die Prüfungen laufen (mit Playwright). Er findet und diagnostiziert Fehler selbst.

Automatik (CI)

Derselbe Test per Befehl, ohne Oberfläche. Läufe lassen sich als Video aufzeichnen und als Nachweis teilen.

ErkenntnisMan kann den «Vertrag» der Oberfläche brechen, ohne die App zu brechen. Der Test schlägt dann trotzdem an. Das Claude-Code-Team zeichnet auf diese Weise praktisch alle Frontend-Änderungen auf.

Agenten, die sich erinnern: Memory und «Dreaming»

2:50 – 3:19Kevin, Engineer, Anthropic

Standardmässig ist jede Agenten-Sitzung isoliert: Was du gestern erzählt hast, weiss der Agent heute nicht mehr. Das lässt sich in zwei Schritten lösen.

Ebene 1: SitzungEine isolierte Unterhaltung, meist vergänglich.
Ebene 2: Memory StoreDauerhafter, dateiähnlicher Speicher. Der Agent liest und schreibt Notizen darin (mit Bash, Suche, Lesen). Die Dateien sind versioniert und von Menschen einsehbar und korrigierbar. Zugriff lässt sich auf «nur lesen» beschränken.
Ebene 3: DreamingEin Hintergrundauftrag, der Notizen und alte Gespräche durchgeht: Fakten prüfen, anreichern (Daten, Namen), Duplikate zusammenführen, Inhaltsverzeichnis anlegen. Das Original bleibt unberührt, das Ergebnis ist ein neuer Speicher.
Demo-Ablauf
  1. Ohne Memory: Agent antwortet auf die Nachfrage «Das weiss ich nicht».
  2. Mit Memory: Agent speichert und findet die Info in der nächsten Sitzung.
  3. Nach Dreaming: Antworten sind vollständiger (Zeitplan, Links, Namen).
Gut zu wissen
  • Ein Dream-Lauf dauert Minuten bis Stunden. Bewusst nicht live.
  • Er verbraucht viele Tokens (laut Referent ca. 95 % aus dem Zwischenspeicher).
  • Günstigere Varianten (z. B. Stapelverarbeitung) werden geprüft.

Wenn Programmieren nicht mehr der Engpass ist

3:19 – 3:46Führungskraft im Claude-Code-Team (Name im Transkript nicht genannt)

Ein Erfahrungsbericht zur Teamarbeit: Früher war Entwicklungszeit knapp und teuer. Heute entsteht Code schnell, und der Engpass wandert zu Prüfung, Review, Sicherheit und Abstimmung.

Früher wichtig

  • Halbjahres-Roadmaps
  • Design-Dokument vor jedem Code
  • Produkt-Reviews
  • Wer hat den Code geschrieben?
  • Strenge Rollengrenzen

Heute im Team

  • Planung «just in time»
  • Prototyp oder Pull Request statt Dokument. «Code gewinnt» die Diskussion
  • Verifikation früh automatisieren («Shift left»)
  • Rollen verschwimmen: PMs coden, Entwickler schreiben Texte mit Claude

Grundsätze des Teams

ThemaPraxis
Code-ReviewClaude übernimmt Stil, Lint, erste Fehlersuche, Tests. Menschen bleiben bei Recht, Sicherheitskritischem, Risikoabwägung und Produktgefühl («Vertrauen, aber prüfen»).
Wer war es?Besser fragen: Was will ich wirklich wissen? (Ursache eines Fehlers? Experte? Kontext?) und genau das automatisieren.
Quelle der WahrheitDer Code selbst. Wer Spezifikationen pflegt, lässt Claude Code gegen die Spezifikation prüfen.
TeamformFlach, eine gemeinsame Mission. Führungskräfte steigen zuerst als Mitarbeitende ein und nutzen das Produkt selbst («Dogfooding»).
ProzesseAusdrückliche Erlaubnis, Prozesse zu streichen. Beispiel: Aus Stand-up und Tabelle wurde ein Skill, der den Stand zusammenfasst.
Alles «claudifizieren»Bei jeder Aufgabe fragen: Könnte Claude das tun oder dabei helfen?

Deine ersten Schritte

Wenn du Claude erst kennenlernst: Diese sechs Dinge kannst du sofort umsetzen, ohne Programmierkenntnisse.

1. Kontext gebenWer ist die Zielgruppe, was ist das Ziel, was ist bereits bekannt? Je mehr, desto besser.
2. Claude befragen lassen«Stell mir Fragen, bevor du anfängst.»
3. Plan zuerst«Zeig mir erst, wie du vorgehen würdest.»
4. Beide Seiten nennenBei Abwägungen Vor- und Nachteile erklären, nicht nur verbieten.
5. Prüfen lassen«Kontrolliere dein Ergebnis gegen meine Kriterien.» Wichtiges immer selbst gegenprüfen.
6. Kleine Aufgaben automatisierenWiederkehrendes als Skill oder Routine festhalten.
Wichtig für den BetriebGib keine vertraulichen Kundendaten ein, solange die Nutzung nicht intern freigegeben ist. Bei sicherheits- oder rechtsrelevanten Ergebnissen entscheidet immer ein Mensch.
